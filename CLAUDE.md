## Current architecture refactor (started 2026-10-09)

Branch `refactor/architecture`. Full audit + phased plan → `Docs/REFACTOR_AUDIT.md` (Phase 0/1). Hard rule: zero gameplay/behavior changes at every step. Status by phase:

- **Phase 2A (done, 2026-10-09)**: `Human.cs` and `Scientist.cs` were ~95% identical (wandering/panic/fleeing zombies/evacuation/boarding transport — the same code in both files). Extracted into a shared `EvacueeBase.cs`; `Human`/`Scientist` are now ~8-line subclasses, whose only own content is a static list (`Human.AllHumans`/`Scientist.AllScientists`) and registering into it via `OnEnable`/`OnDisable`. Field names and types weren't changed — serialized values on `Human.prefab`/`Scientist.prefab` survive the refactor with no extra action (verified).
- **Phase 2B (done, 2026-10-09)**: removed GC allocations in combat coroutines with no behavior change. `WaitForSeconds` is now cached (not re-created on every shot/attack/hit) in `Zombie.cs`, `Sniper.cs`, `Soldier.cs`, `CombatHelicopter.cs`, `CarController.cs`, `Barricade.cs`, `Bait.cs`. New `SharedMaterials.cs` — a single shared `Material` for "Sprites/Default" (like `VfxManager.EnsureMaterial`), used instead of `new Material(Shader.Find(...))` for every placed card in `Sniper.cs`, `Soldier.cs`, `CombatHelicopter.cs`, `Bomb.cs`, `Bait.cs`, `InputManager.cs`. **Exception**: `HelicopterController.cs` (landing marker) mutates `.material.color` directly — a shared material instance can't be used there (it would leak the color onto every other instance); only `Shader.Find` is cached there.
- **Phase C (done, 2026-10-09)**: `Physics.OverlapSphere`/`RaycastAll` replaced with `*NonAlloc` + a reusable buffer, with no behavior change. New `PhysicsNonAlloc.cs` — a helper that grows the caller's own `ref` buffer if it fills up completely (otherwise the `NonAlloc` variants would silently truncate the result with a large number of colliders — this locks in exact behavioral parity with the unbounded `Physics.OverlapSphere`). The buffer is a field on the specific call site, not shared: `Bomb.cs`, `Barricade.cs`, `CombatHelicopter.cs` — one buffer per class (calls within one method run sequentially, with no yield between them); `CarController.cs` — two separate buffers (`crushHitsBuffer`/`boardingHitsBuffer`), because the boarding check reads its result via `yield return StartCoroutine(...)` and can't share one with the per-frame run-over check. This closes the only confirmed truly per-frame `OverlapSphere` allocation (`CarController.cs:148`, inside `Update()`). `Sniper.cs`: `RaycastAll` → `RaycastNonAlloc`, plus `System.Array.Sort` with a lambda replaced by a cached `IComparer<RaycastHit>` — removes the hidden `Comparer<T>` wrapper allocation that .NET creates for the `Comparison<T>` overload.
- **Not included in Phase C**: `ZombieBoss.cs:129` has the same `Physics.OverlapSphere` pattern, but wasn't in the agreed file list for this phase (see `Docs/REFACTOR_AUDIT.md` §Phase C) — don't touch without a separate "go".
- **Phase D (done, 2026-10-09)**: deduped the "scan a static `AllX` roster, keep the nearest" pattern into a new `TargetScanUtil.FindNearest<T>()` (generic, with an optional `accept` predicate for site-specific differences like Soldier's `IsDead` check or the bait attraction radius). Applied in `EvacueeBase.cs` (panic target), `Soldier.cs` (`FindTarget`), `CombatHelicopter.cs` (`FindClosestZombie`), `Zombie.cs` (bait search, `FindClosestVictim`, `TryFindNearestBarricade`). Same call sites, same frequency, same tie-break (on equal distance, keep whichever was found first) — behavior unchanged. **Deliberately left alone**: the multi-criteria threat scoring in `Sniper.cs`, the boolean "is there any zombie within radius at all" check in `HelicopterController.cs` (early `break`, not "find the nearest"), and the "collect every match within radius and act on each" loops in `CarController.cs`/`HelicopterController.cs` — these are a different shape of algorithm, not a copy of the same pattern; forcing them through `FindNearest` would change their early-exit characteristics with no benefit from the dedup.
- **Phase E (done, 2026-10-09)**: `EnergyManager` (in-combat energy, which nothing has spent since around Phase 2A — the one spend call is commented out in `CardUI.cs`) removed entirely along with its UI. Confirmed: the `EnergyBar` hierarchy (`Canvas/EnergyBar/Fill Area/Fill` + `EnergyText`) in `Gameplay.unity` was already disabled (`activeSelf: 0` on `EnergyBar` itself) — the bar was never physically shown, yet `EnergyManager.Update()` still regenerated its value into the void every frame. Removed: `EnergyManager.cs`, its component on `Managers`, the `EnergyBar` HUD hierarchy, the `manaText`/`manaFillBar` fields + the `OnEnergyChanged` subscription in `UIManager.cs`, the F4 "Fill Energy" cheat in `CheatManager.cs`. **Don't confuse with, and don't touch**: `PlayerProfile.currentEnergy`/`maxEnergy` — a different system (the meta-gate on "attempting to play a level"), left as-is.
- **Phase F (done, 2026-10-09)**: `Docs/mechanics/persistent-modifier-store.md` marked archived — it specified a separate persistent store for the Talent Tree, but that question was resolved differently (see the meta-layer item above): modifiers live in `MetaRuntime.Modifiers`/`MetaProgressionState`, not in that store. The file is kept as an archived design rationale, with a "resolved differently" status note at the top. This was the last phase of the `Docs/REFACTOR_AUDIT.md` plan — Phases A–F are all complete.

## Architecture patterns worth knowing

- **Shared civilian AI**: see "Phase 2A" above — `EvacueeBase.cs` is now the single place with Human/Scientist logic.
- **Modifiers/flags (per-run, roguelite)**: `RunSessionData.cs` (`Assets/Scripts/Roguelite/`) — a singleton with `AddModifier(key, value)` / `GetModifier(key, default)` / `SetFlag(id)` / `HasFlag(id)`. Card controllers (`Sniper.cs`, `Barricade.cs`, `CombatHelicopter.cs`) read from it via `RunSessionData.Instance?.GetModifier(...)`. `Instance` is currently null (roguelite is frozen for MVP). **This is NOT a prototype of a future persistent store** — a persistent store for the Talent Tree is already implemented separately, see the next item (the old wording here and in `Docs/mechanics/persistent-modifier-store.md` was accurate as of 08-23, but stale by 10-09 — the question is settled).
- **Meta layer "city" + Talent Tree (implemented, but not mentioned in this file until 2026-10-09)**: `Assets/Scripts/Meta/*` — restorable buildings (`Meta/Base/BaseView.cs`, `BaseHouseView.cs`, `Meta/City/MetaBuildingPanel.cs`) and a skill tree (`Meta/Research/MetaSkillTreeScreen.cs`), applied globally to every card via `MetaRuntime.Modifiers` (`Meta/Modifiers/MetaModifiers.cs`) — this is exactly the mechanism that settles the question from `Docs/mechanics/persistent-modifier-store.md`. Its own save, separate from `PlayerProfile`: `MetaProgressionState` + `MetaSaveService` (`Meta/Save/*`), one JSON blob under the key `"MetaProgression"`. Composition root — `MetaRuntime.EnsureInitialized()`. UI is built entirely in code via `Meta/UI/MetaUI.cs` (no scenes/prefabs). Full system map → `Docs/REFACTOR_AUDIT.md` §1.
- **Card stats**: `CardData.cs` — `StatType` enum + `CardStat{ baseValue, valuePerLevel, unitSuffix }`, value at a given level = `baseValue + valuePerLevel * (currentLevel - 1)`. `CardCategory` (Evacuation/Combat/Utility), `CardRarity` (Common/Rare/Epic/Legendary).
- **Sound / haptics / VFX / settings**: everything goes through the `Feedback.Play(FeedbackEvent.X[, worldPos])` facade (`Assets/Scripts/Feedback/`) — the event table lives in `Feedback.cs`. Managers create themselves (`RuntimeInitializeOnLoadMethod`), scenes aren't touched. A new sound/effect = one row in the table + one hook line in code. Placeholder sounds are synthesized in code; the real sound is a file at `Resources/Audio/Sfx/<SfxId>`. New `AudioSource`s must check `AudioManager.SfxAllowed`. Details → `Docs/mechanics/feedback-audio-vfx-haptics.md`.
- **Saves**: `PlayerProfile.cs` — a singleton, `DontDestroyOnLoad`, persists via `PlayerPrefs` + `JsonUtility` (lists like `ownedCardsProgress` are serialized through a `SerializationWrapper<T>` wrapper). Currency (People/Scientists) lives here too, read/written via `MetaRuntime.Currency` rather than directly — don't bypass the facade. **Important**: this isn't the only persistent layer — `MetaProgressionState` (meta progress: buildings, tree nodes) is saved separately, see the meta-layer item above. The question of "where does new persistent state go" is decided case by case (talent-tree-like → next to `MetaProgressionState`; currency/cards/world-map position → `PlayerProfile`); don't change the save format without an explicit request.

## Responsive layout (mobile UI, portrait-only, done 2026-10-10)

Full responsive pass: portrait lock, SafeArea, aspect-aware CanvasScaler, fit-to-width camera, a real hit test for the card panel instead of `Screen.height * 0.25f`, a fix for the tutorial banner. Rules below so future UI work doesn't break what's already fixed.

- **Screen zones**: top = HUD (timer, counters), bottom = card hand (`CardsPanel`), center = map/city. Edge-anchored elements attach to the safe area's edges, not to absolute screen pixels.
- **Portrait-only**: `ProjectSettings.defaultScreenOrientation = Portrait` (0), every other `allowedAutorotateTo*` is disabled except `Portrait`. Change this via the `PlayerSettings` API (`unity command eval`), not by hand in `ProjectSettings.asset` — the Editor keeps these values in memory and doesn't re-read the file on the fly.
- **SafeArea**: `Assets/Scripts/UI/SafeArea.cs` — placed on a container that pulls `anchorMin/Max` in to `Screen.safeArea`; ALL children of the container inherit the inset, but objects that are SIBLINGS of the container do not (this was the real cause of a bug in `Gameplay.unity`/`MainMenu.unity` — HUD elements sat next to the Container instead of inside it). Currently: `Gameplay.unity/Canvas/SafeAreaContainer` holds the whole HUD/card hand/popups except the frozen roguelite pieces (`XPBar`, `LevelUpScreen` — don't touch those, they stay direct children of `Canvas`); `MainMenu.unity/Canvas/Container` holds everything, including the counters/`BottomNav`/popups.
  - **Exception**: `TutorialManager`'s `DialogPanel` (the tutorial banner: character portrait + text) is part of the `TutorialCanvas` prefab instance; Unity **won't allow** reparenting an object from inside a prefab instance into a new safe-area container (`"Setting the parent of a transform which resides in a Prefab instance is not possible"`). Fixed in code instead: `TutorialManager.ShowStep()` adds the safe-area inset (via `Screen.safeArea` + `Canvas.scaleFactor`) directly into `anchoredPosition` for Top/Bottom positions — see `GetVerticalSafeAreaInsetsInCanvasUnits()`. If a similar fix is needed for another object inside a prefab instance — use the same pattern (inset in code, not scene reparenting).
- **CanvasScaler**: `Assets/Scripts/UI/AspectAwareCanvasScaler.cs` — on every Canvas that has a CanvasScaler (`Gameplay/Canvas`, `MainMenu/Canvas`, `MainMenu/TutorialCanvas`). Compares the current screen aspect to the `referenceResolution` aspect (1080x1920) and switches `matchWidthOrHeight` between 0 (MatchWidth) and 1 (MatchHeight) — keeps 16:9–20:9 phones and 4:3 tablets on one setup with no manual tuning. Adding a new Canvas with a CanvasScaler — add this component too. Nested Canvases without their own CanvasScaler (e.g. `CardUI`'s drag-sort canvas) don't need it — they inherit scale from the parent.
- **Camera (fit-to-width)**: `Assets/Scripts/CameraFraming.cs` + `CameraController.SetupCamera()` + `CameraSwitcher`. **Important**: this is NOT a recomputation of the "ideal" frame from level geometry — bounds measured from the `Building` tag + spawn points were tried, but on Level_1 that went wildly wrong (one tagged building sits ~40° off-axis from the authored camera — level content isn't the source of truth for what the camera should show). Instead the code trusts the authored `LevelData.orthographicSize`/`cameraPosition`/`cameraFieldOfView` as correct for the 1080x1920 reference aspect and only EXPANDS the frame (the already-authored positioning is a fallback/minimum — it's never shrunk or moved closer). `LevelManager.GetReservedScreenFractions()` measures the real on-screen height of the HUD (`topReservedUI` — an array of RectTransforms, currently `TimerText`+`RescuedCounter`) and of the card hand (`CardManager.cardsPanel`) via `GetWorldCorners` (Screen Space - Overlay → already screen pixels, the safe area is already baked in). If you add a new top-HUD element that could stick out below the current ones — add it to `LevelManager.topReservedUI` (via the inspector, or `unity command set_serialized_field`/`SerializedObject` — it's an array of object refs).
- **Card hand / input zone**: `InputManager.cs` (2 places) and `CardUI.cs` used to gate "is this the UI zone" via `Screen.height * 0.25f`. Now — `CardManager.IsScreenPointOverCardsPanel(screenPoint)`, a real `RectTransformUtility.RectangleContainsScreenPoint` against the actual `cardsPanel`. If another place needs a similar check — use this method, don't introduce another magic percentage.
- **Known verification limits (2026-10-10)**: the Device Simulator package (`com.unity.device-simulator`) isn't installed — verification across 5 target resolutions (1080x1920, 1080x2400, 1170x2532, 750x1334, 1536x2048) was done via `capture_game_view` with the real `Screen.width/height` for that size, but WITHOUT simulating a real notch/cutout (the Editor without Device Simulator reports `Screen.safeArea` = the whole screen, inset = 0). That means: proportions/aspects/the safe-area MECHANISM are verified, but whether the safe area actually pulls content in under a real notch on an actual 1170x2532 device — not verified. If an exact notch check is needed — install Device Simulator (ask Vlad) or test on a real phone.
- **`unity command eval`**: `Transform.SetParent` on an object inside a PrefabInstance silently fails (the object stays where it was) — neither a bare `eval` nor the `set_parent` command can move a prefab instance's child out to a different parent. If such an object needs to be moved — either unpack the instance (`PrefabUtility.UnpackPrefabInstance`, which changes its link to the prefab — ask Vlad first), or solve it in code (as with `DialogPanel` above), not in the scene.

## Git in this repository (only if working through the mounted folder, not Vlad's regular local git client)

- A wide/unbounded `git status` and plain `git commit` reliably **hang** on this mount (a real `unlink` isn't supported, stale lock files). Don't guess — if a command hasn't returned in a reasonable time, don't just repeat it as-is.
- The way that works to commit: `git write-tree` → `git commit-tree <tree> -p <parent-sha> -F <msgfile>` → `git update-ref refs/heads/<branch> <new-sha>`. Ignore `unable to unlink tmp_obj/*.lock` warnings.
- On errors like `Unable to create .git/index.lock/HEAD.lock/refs/heads/main.lock: File exists` — rename (`mv`) the lock file out of the way (a new suffix each time, `rm` doesn't work either) and retry. Don't gate the `mv` on an `ls` with `&&` across multiple files — move each one separately.
- The same thing can bite Vlad's regular local git client (GitHub Desktop etc.) too — a `.git/HEAD.lock` left behind by a Cowork/Claude Code session blocks a local commit with "A lock file already exists". If Vlad reports this after a session that touched the repo — check/rename `.git/*.lock` first.
- **Known junk in `refs/heads`** (found 2026-08-29, not cleaned up): `main.lock.stale` and `main.lock.stale3` — these are renamed stale lock files from earlier sessions; git sees them as real branches (`git branch -a` will show them). They are NOT real branches — ignore them, don't merge them. `origin/main` matched local `main` at the time of checking (the repo was pushed, up to date).
